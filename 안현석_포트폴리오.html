소개

운영 장애를 로그와 데이터로 좁히고, 정상 상태까지 검증합니다.

망분리 공공 시스템을 6개월간 운영하며 암호화 모듈 라이선스 만료로 평문 저장되던 약 50건을 로그로 찾아냈습니다. 서버를 한 대씩 순차 교체하고, 데이터를 재암호화한 뒤 건별로 정합성을 확인했습니다.

동시 요청·재시도·타임아웃에서도 데이터와 비용이 어긋나지 않게 설계합니다.

성능 병목은 실제 실행 환경에서 측정하고 구조로 개선합니다.

Projectree의 3D 트리에서 라벨 DOM 4,000개가 평균 9.3 FPS를 만든다는 것을 빌드 환경에서 측정했고, 렌더링 구조를 바꿔 같은 조건에서 45.4 FPS로 다시 검증했습니다.

및 성능 개선
1. 유료 AI 호출의 중복 실행과 이중 과금 경로 차단
  • 문제: AI 힌트는 느리고 호출마다 비용이 듭니다. 같은 입력의 동시 요청, 타임아웃, 서버 재시작, DB 저장 실패가 겹치면 같은 요청을 여러 번 유료 호출하는 경로가 생길 수 있었습니다.
  • 해결:
    • 정규화한 입력의 SHA-256 해시에 유니크 제약을 걸어, 같은 입력의 생성 주체를 하나로 제한
    • GENERATING / READY / FAILED 상태와 generation 번호로 펜싱해, 장애 후 다른 요청이 이어받아도 늦게 끝난 이전 작업자가 결과를 덮어쓰지 못하게 함
    • 결과 저장에 실패해도 기록을 지우지 않아 같은 유료 요청이 곧바로 반복되지 않게 함
    • Python 담당자와 응답 코드의 의미를 맞추고, AI SDK 자체 재시도를 꺼 Spring·Python·SDK 재시도가 겹쳐 불어나지 않게 함
  • 결과:
    • 같은 입력 동시 5건 요청 → AI 호출 1회 (실제 PostgreSQL 통합 테스트로 검증)
    • 힌트 1건당 모델 호출 상한 최대 12회 → 4회 (SDK 기본 재시도를 켰을 때와 비교한 설계 상한)
    • 장애 상황에서도 앱은 500 대신 "생성 중 / 힌트 없음" 상태를 받음
2. 사진 해석을 비동기 작업으로 분리
  • 문제: 사진 해석은 VLM 호출에 수십 초가 걸려 요청 안에서 처리하면 스레드와 DB 커넥션을 오래 점유합니다. 같은 문제에 시작 요청이 겹치면 해석 작업이 중복될 수도 있었습니다.
  • 해결:
    • 해석을 작업(Job)으로 분리하고 대기 → 실행 → 성공/실패 상태 전이를 설계
    • 문제당 활성 작업 1개를 부분 유니크 인덱스로 제한
    • Python 503은 1회만 재시도하고, 오래 멈춘 작업은 스케줄러가 정리하도록 구성
  • 결과: 같은 문제에 시작 요청이 동시에 와도 작업 1개, 모두 같은 jobId를 받는 것을 통합 테스트로 검증, 서버 재시작 뒤에도 복구 가능한 작업 흐름 확보
3. 동시 요청·재전송 감사와 정합성 보강
  • API 구현 뒤 정상 요청뿐 아니라 동시에 오거나 재전송되는 상황을 따로 감사했습니다.
  • 같은 폴더 같은 이름 동시 등록: 유니크 인덱스 + flush로 즉시 확인 / 폴더 삭제 vs 문제 등록·이동: 폴더 행 잠금과 잠금 순서 통일
  • 풀이 화면 이어 저장: revision 기반 낙관적 동시성, 불일치 시 409 / 학습 완료 중복 요청: 시도 행 잠금 후 최초 결과 재사용
  • 주요 생성 API 재전송: Idempotency-Key + 정규화된 요청 해시. INSERT … ON CONFLICT로 선점하고 선점 기록을 업무 트랜잭션과 함께 롤백해, 실패한 요청은 같은 키로 재시도 가능
  • 이미지 업로드는 스트림으로 처리하고, S3 업로드 후 DB 저장이 실패하면 업로드한 파일을 정리
